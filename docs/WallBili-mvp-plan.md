**WallBili 初版开发计划：三阶段 MVP**

版本：初版。建立日期：2026-10-14；技术确认与环境记录更新：2026-10-15。此文档用于后续应用开发；工具初始化已执行。本次 init 分支仅交付规划与交接文档，尚无可运行应用。云端代码草稿未完成构建与验收，未随文档提交。当前进展见 [临时交接说明](../TEMP-HANDOFF.md)。

技术栈已于 2026-10-15 确认：[C#/.NET 10 + WPF + SQLite + mpv](./WallBili-stack-proposal.md)。[云端初始化记录](./environment-handoff.md)包含三个环境检查、WPF 编译和短时远程媒体解码的结果。本计划中“保持灵活”的表述继续适用于复用方式和视觉细节，应用主栈按已批准方案收敛。

**目标与已确定约束。** 在 Windows 10/11 上，从 B 站取得用户选定的视频内容，管理合集和播放队列，将播放中的视频输出显示在真正的桌面壁纸层，并保留桌面图标交互。应用最终可在登录桌面后恢复运行。WallBili 启动、播放和退出时，Wallpaper Engine 可继续正常运行，其设置和窗口结构受到保护。

A/B/C/D 的复用组合和 V 视觉细节继续按证据与实现成本确定；T 已确认采用 C#/.NET 10 + WPF + SQLite + mpv，桌面显示通过 C#/Win32 宿主承载。视频做壁纸已经确定；首条端到端验收链路使用一条 B 站视频进入壁纸层，作为能力验证，不锁定最终的界面风格或视频呈现分支。Wallpaper Engine 是兼容对象，计划不要求开发它的接口集成或自定义壁纸。

**MVP 闭环。** 用户添加视频或合集链接 → 展开可播放条目 → 加入并维护队列 → 取得当前条目的音视频播放资源 → 播放会话输出视频 → 桌面宿主承载画面 → 切换条目与恢复运行。

首版以明确选择的 UP 主合集/系列和视频为内容范围。合集的单位是视频或分 P；包含多首歌的长视频作为一条播放项，不在初版增加自动识别歌曲和拆分曲目的工作。首版可先接入一种实际有效的合集类型，之后扩展收藏夹或 UP 主新投稿筛选。

```mermaid
flowchart LR
    I[视频 / 合集输入] --> S[内容接入]
    S --> L[本地合集与视频目录]
    L --> Q[播放队列]
    Q --> R[获取当前音视频资源]
    R --> P[统一音视频播放会话]
    P --> W[桌面视频输出]
    E[Wallpaper Engine 独立运行] -. 共存验收 .-> W
```

**实现边界。** 用四个小模块保留选型空间，每个阶段先完成一条可运行路径。

| 模块 | 责任 | 最小接口示意 | 可复用的部分 |
|---|---|---|---|
| 内容接入 | 视频身份、元数据、分 P、合集分页、播放资源获取 | `getVideo(input)`、`listCollection(source, cursor)`、`resolveMedia(contentKey)` | Biu、其他有效实现或自行编写适配器；先验证实际接口 |
| 列表与存储 | 来源、合集快照、条目、队列、当前项和恢复进度 | `importCollection()`、`refreshCollection()`、`enqueue()`、`saveProgress()` | 可采用现有队列/存储实现，或参考行为重写；核对许可 |
| 播放控制 | 一次音视频会话、切歌、暂停、seek、重连与结束事件 | `load(media)`、`play()`、`pause()`、`seek()`、`onEnded()` | 已选 mpv，通过 C# JSON IPC 控制 |
| 桌面输出 | 承载视频、目标显示器、图标交互、启停与窗口清理 | `attach(videoOutput, display)`、`detach()`、`onDisplayChanged()` | 已选 C#/Win32 自建宿主；窗口绑定方式须通过 Wallpaper Engine 共存原型 |

接口示意用于说明职责，代码语言按已确认的 C# 执行，不强制复杂进程结构或插件框架。既有列表实现可以作为行为参考；直接复用代码时兼顾技术边界和许可。资料参考、源代码复制、整项目改造分别核对对应许可，不能默认都按当前仓库的 MIT 发布。

列表保存内容身份，临时播放资源在需要时获取。至少区分以下对象：

- `ContentKey`：平台 + BVID + CID，唯一标识一个视频分 P。
- `Source`：所选合集/系列的身份、来源 UP 主、刷新状态。
- `Entry`：内容身份、标题、UP 主、时长、可用状态。
- `Queue`：按顺序排列的内容身份、当前位置、播放模式。
- `PlaybackProgress`：当前内容身份、进度、音量和恢复状态。
- `MediaSession`：本次解析到的视频/音频资源、必要请求条件、可用格式及到期信息（若有）。账户会话保留在接入模块内。

持久化采用 SQLite 与 Microsoft.Data.Sqlite。队列持久化不绑定临时 CDN URL，刷新来源不重置当前播放进度。显示模式变化由桌面模块处理，队列只关心哪个内容正在播放。

**阶段一：拿到 B 站内容，并证明音视频可播放。**

当前优先级：先打通公开内容的最小播放链路，再扩展合集与桌面输出。先分别验证“持续发现内容”和“持续播放内容”：多样例元数据与分 P → 解析音视频 → 实际播放与切歌 → 资源重新解析与恢复。HTTP 412 与云代理 CONNECT 403 分别记录，不混为接口失效。

阶段目标是验证数据来源和媒体链路，为内容适配与复用提供证据。成果可以是 C# 测试驱动程序与简单调试播放器，无需先设计完整桌面 UI。

执行顺序：

1. 检查可访问网络、实际接入方式和公开样例。B 站 API、网页和实际返回的两个媒体 CDN 已保存到环境草稿；后续遇到新主机按真实请求结果追加。
2. 输入一条视频链接或 BVID，取得标题、UP 主、时长、分 P 与 CID。
3. 按所选接入实现取得可用的视频和音频资源，以及播放所需的正常请求条件。
4. 用调试播放器实际显示视频并播放音频，验证启动、暂停、继续和 seek。
5. 补一个分 P 样例与一种合集/系列的读取探针，为阶段二确认可支持的来源类型。
6. 重新获取同一视频的播放资源，验证列表可根据内容身份发起新的播放请求。

交付物：可重复执行的内容探针、统一的内容/媒体数据结构、可播放的调试样例、按能力分别记录的接入验证结果，以及“继续复用 Biu / 换候选实现 / 编写适配器”的证据。

验收门槛：

- 至少一条公开视频能实际显示画面并出声，记录使用的格式与清晰度；只拿到 URL 或 HTTP 成功码不算通过。
- 一个分 P 样例的 BVID/CID 关系正确，切换分 P 后播放目标正确。
- 一种合集/系列能读取条目；若分多页，需要验证分页规则。
- 同一内容可以重新解析播放资源，准备好链接到期后的恢复路径；尚未发生的自然到期不声称已验证。
- 返回不可访问、内容失效、格式不支持或需要登录时，结果有明确分类。公开内容与登录内容分别记录结论。

Biu 已核查的核心请求在自身源码中，直接调用 B 站；资料库下线不必然导致代码失效。初期连接代理 403 已不再代表全部当前结果：2026-10-15 已读取样例公开网页和分 P，按 Biu 的签名播放方式取得音视频并用 mpv 完成短时远程解码。直接元数据接口仍为 HTTP 412；完整合集、登录和 Windows 播放尚未覆盖。环境探针的局部成功不代替阶段一全部验收。

阶段一通过后，选择一个确实有效的内容实现继续阶段二。若某类来源不可用，可先保留实际有效的来源范围，并明确未覆盖的能力；不把未经验证的接口纳入完成声明。

**阶段二：维护合集、视频目录和播放队列。**

阶段目标是把“单条能播”变成“用户选择来源后能够连续播放”。这部分可以复用，也可以参考他者的行为自行实现；测试围绕对用户可见的列表与播放行为。

执行顺序：

1. 导入所选合集/系列，取得条目并保存来源关系；分 P 展开为正确的视频身份。
2. 建立列表展示与最小编辑能力：添加、删除、排序、加入队列和查看当前项。
3. 建立队列推进：顺序播放、下一项/上一项、列表循环；随机模式可在这一阶段随后增加。
4. 连接阶段一的调试播放器，由播放结束事件推进队列，而不是用固定时长计时切歌。
5. 保存队列与当前进度，重启后恢复；失效条目有状态记录，可跳过且不会使队列停在无限重试中。
6. 支持手动刷新合集：新增条目能出现，同一内容不因刷新被重复导入，当前项和进度保留。

交付物：合集/目录模块、持久化队列、连续视频播放、恢复行为和简单可操作界面。后台使用需要的托盘与快捷控制可按所选应用壳逐步接入。

验收门槛：

- 用至少两个所选来源或两个合集建立包含多条视频的队列，能连续播过多个条目。
- 添加、删除、排序和切换当前项均能产生预期行为；删除正在播放的条目时有确定规则，例如推进到下一项，无下一项则停止。
- 反复刷新同一来源，条目身份稳定且不会不断增加重复内容。
- 重启后能恢复队列、当前内容与合理的进度；用户主动停止与异常中断应按明确的恢复规则处理。
- 构造一个失效条目，能够标记并推进到可播内容；失败结果不能被保存成“已成功播放”。

为了降低阶段三的可行性风险，在完整 UI 和大量队列功能投入前，用短本地测试视频做一个桌面共存小原型。它只验证候选显示后端在 Wallpaper Engine 运行时能否启停、保留图标交互并清理自身窗口；完整 B 站视频到壁纸的串接仍在阶段三交付。小原型发生冲突时更换或调整显示后端，列表模块可以继续独立开发。

**阶段三：将播放会话的视频输出接入桌面壁纸层。**

阶段目标是连接前两阶段，形成真正的 MVP。这里的“转发”指播放会话的视频输出进入桌面宿主；是否需要本机中转或缓存，由格式和请求条件的兼容测试决定。

执行顺序：

1. 根据共存小原型确定 Win32 窗口绑定和层叠方式，由自建宿主 HWND 承载 mpv 视频输出。首版先完成一块目标显示器；显示器可配置，复杂多屏布局后续扩展。
2. 将阶段二当前项的视频输出附着到桌面壁纸层，保留桌面图标交互，提供填充/适应画面的基本选择。
3. 保持音视频由同一播放会话或受同一时钟控制。切歌、暂停、seek 和恢复同时作用于对应音画，WallBili 只产生一份音乐音频输出。
4. 区分播放状态与画面承载状态：关闭或隐藏桌面画面不应丢失队列；继续听音乐的行为由播放设置控制。
5. 处理真实生命周期：显示器变化、睡眠恢复、Explorer 重启、网络中断、流地址失效。重连通过内容身份重新解析资源，再恢复当前项。
6. 加入后台入口、登录自启开关和恢复队列的启动流程，串接最终用户路径。
7. 用打包后的 Windows 应用验证整个闭环，检查退出后清理 WallBili 自己的窗口和进程。

交付物：可运行的 Windows MVP、最小使用说明、来源导入与队列操作入口、桌面视频模式、后台恢复流程和共存验收记录。

验收门槛：

- 一条 B 站视频能沿“输入/合集 → 队列 → 播放会话 → 桌面壁纸”链路播放，桌面图标可点击。
- 队列中的视频切换能更新壁纸画面和音频；暂停/继续与 seek 不产生独立播放器互相漂移或双重音频。
- Wallpaper Engine 先启动和后启动两种顺序都能继续运行；WallBili 不关闭其进程、不替换其壁纸设置、不破坏其窗口结构。退出 WallBili 后原有壁纸仍可正常显示。
- 同屏的显示层叠行为在 Windows 原型中确定；不能只用 Wallpaper Engine 的 PID 存在来证明兼容。
- 登录后能恢复所选队列；网络晚就绪时等待并恢复。记录登录至播放的实测时间，不预先将目标时限当作已通过结果。
- 至少一次短时断网、一次睡眠恢复、一次 Explorer 重启验证；再做至少两小时连续运行和不少于 20 次主动切换，确认进度恢复与资源没有持续增长。

音画同步测试覆盖开播、seek、切歌和恢复后的位置对应，初步可设音画误差目标不超过 200 毫秒，再按所选引擎的测量方法记录结果。资源测试固定分辨率/帧率，例如 1080p/30fps，分别记录 WallBili、Wallpaper Engine 与二者同时运行的 CPU/GPU/内存。阶段三首版保证一块目标屏幕；多屏全面兼容和极端恢复情形的范围按真实问题进一步扩展。

**首版范围与后续扩展。** 首版交付视频内容接入、一种有效合集类型、队列管理、连续音视频播放、持久化恢复、单屏视频壁纸、后台运行及 Wallpaper Engine 共存。之后再扩展 UP 主新投稿自动筛选、定时订阅刷新、更多来源类型、多平台、歌曲识别与歌词、复杂主题、自动更新、设备同步和更完整的多屏策略。

**技术决策发生的位置。** 这些决定用于实现时选择，不要求现在确认，也不在阶段中逐项向用户索取意见。

| 决策 | 证据取得时机 | 选择原则 |
|---|---|---|
| Biu 是否继续复用 | 阶段一接口与实际音视频通过后 | 接入有效才继续；资料引用和源码存在不代替实测 |
| 复用、改造、参考或自研 | 每个模块开始实现时 | 比较有效性、许可、改造量与后续维护；无需全项目统一采用一种方式 |
| 播放引擎 | 已确认 mpv；阶段一/三继续验具体行为 | 云端解码与 IPC 已通过；音画输出、真实 seek 与桌面输出继续在 Windows 验证 |
| 显示实现 | 已确认 C#/Win32 宿主；具体绑定方式由早期原型确定 | 优先真实桌面、图标交互和 Wallpaper Engine 共存结果 |
| T 技术栈 | 2026-10-15 已确认 | 按 C#/.NET 10、WPF、SQLite、mpv 执行 |
| V 视觉细节 | 视频能稳定进入壁纸层后 | 视频壁纸是固定目标，画面布局与呈现形式后续迭代 |

若出现无法满足硬约束的证据，先形成具体的失败记录与候选替代方案，再留给最终分支决策。不会把关闭 Wallpaper Engine 或将真正壁纸改成普通全屏窗口视作兼容问题已经解决。

**开发与验证环境。** 云端已准备 .NET、锁定的 NuGet 依赖、mpv 和 FFmpeg，三个环境检查与 WPF 跨平台编译通过，并完成样例媒体短时远程解码。部分 B 站接口仍有访问限制。Windows 实际音画输出、桌面宿主及 Wallpaper Engine 共存须在 Windows 本机验证。工具初始化、草稿与后续发布分别记录；继续使用现有隔离工作区的 checkout。

各阶段分别保留输入样例、执行方式、实测结果与未覆盖的能力。阶段一交付“内容与媒体有效”，阶段二交付“列表能够驱动连续播放”，阶段三交付“视频真正进入桌面且与 Wallpaper Engine 共存”；三者通过后才称 MVP 闭环完成。
